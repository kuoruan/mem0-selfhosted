## Architecture Overview

```
┌─────────────────────────────────────────────────────┐
│                   Docker Compose                     │
│                                                     │
│  ┌───────────┐    ┌───────────┐    ┌─────────────┐  │
│  │ Dashboard  │───▶│  mem0 API │───▶│  Postgres   │  │
│  │ (Next.js)  │    │ (FastAPI) │    │ (pgvector)  │  │
│  │ :3000      │    │ :8888     │    │ :8432       │  │
│  └───────────┘    └─────┬─────┘    └─────────────┘  │
│                         │                           │
│                   ┌─────┴─────┐                     │
│                   │  SQLite   │                     │
│                   │ (history) │                     │
│                   └───────────┘                     │
└─────────────────────────────────────────────────────┘
```

**Three core containers:**

| Container | Image | Port | Role |
|-----------|-------|------|------|
| `mem0` | `ghcr.io/kuoruan/mem0-api-server` | 8888→8000 | FastAPI server — REST API, MCP endpoint, auth, OpenAPI docs |
| `mem0-dashboard` | `ghcr.io/kuoruan/mem0-dashboard` | 3000 | Next.js admin dashboard |
| `postgres` | `pgvector/pgvector:pg17` | 8432→5432 | PostgreSQL 17 + pgvector 0.8.0 — vector storage and app metadata |

**Data storage:**

- **PostgreSQL** (pgvector) — memory vectors, users, API keys, permissions, request logs
  - Memory vectors live in `POSTGRES_DB` (default `postgres`) under the `memories` collection
  - App data (users, keys, permissions, logs) lives in a separate `APP_DB_NAME` database (default `mem0_app`)
- **SQLite** — memory change history (`history/history.db`), maintained internally by the mem0 SDK

## Prerequisites

- **Docker** 20+ and **Docker Compose** v2
- At least one LLM provider API key (OpenAI by default)
- Recommended RAM ≥ 2 GB

| Image | Registry URL |

## Deployment

### Option 1: Docker Compose (Recommended)

Docker Compose orchestrates all three containers, handles networking, and
persists data in a named volume. This is the recommended path for most users.

#### Step 1 — Prepare the environment file

```bash
cd server
cp .env.example .env
```

Edit `.env` — the following are **required**:

```bash
# Postgres — compose will refuse to start without this
POSTGRES_PASSWORD=change-me-to-a-strong-password

# JWT signing secret — generate with: openssl rand -base64 48
JWT_SECRET=paste-the-output-here

# At least one LLM provider key (OpenAI is the default)
OPENAI_API_KEY=sk-...
```

#### Step 2a — Quick start with `make bootstrap`

The fastest path: starts the stack, creates the first admin, and issues an API
key — all in one command.

```bash
cd server
make bootstrap
```

The terminal prints credentials **once**:

```
=== Ready ===
Email:      admin@mem0.dev
Password:   <auto-generated>
API Key:    m0sk_xxxxxxxxxxxxxxxx
```

> ⚠️ Save these immediately — the API key cannot be recovered later.

Override the defaults:

```bash
make bootstrap EMAIL=admin@company.com PASSWORD='your-password' NAME='Admin'
```

Machine-readable JSON output (for scripts):

```bash
OUTPUT=json make seed
```

#### Step 2b — Browser wizard

If you prefer a GUI walk-through:

```bashbash
cd server
make up
```

Then open `http://localhost:3000` and follow the setup wizard to create an
admin account and configure your use case.

#### Step 3 — Verify

```bash
make health
# API:       200
# Dashboard: 200
# Postgres:  ok
```

Local URLs after startup:

| Service | URL |
|---------|-----|
| Dashboard | http://localhost:3000 |
| API | http://localhost:8888 |
| OpenAPI docs | http://localhost:8888/docs |
| MCP endpoint | http://localhost:8888/mcp |

#### Teardown

```bash
make down      # stop containers, keep data
make clean     # stop containers AND wipe the Postgres volume
```

### Option 2: Manual Docker Run

For environments where Compose is unavailable or you want to use an external
Postgres instance.

#### Using the pre-built images

```bash
# 1. Create a network
docker network create mem0-net

# 2. Start Postgres (with pgvector)
docker run -d --name mem0-postgres \
  --network mem0-net \
  -e POSTGRES_PASSWORD=your-password \
  -v mem0_pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  pgvector/pgvector:pg17

# 3. Start the API server
docker run -d --name mem0-api \
  --network mem0-net \
  --env-file server/.env \
  -p 8000:8000 \
  ghcr.io/kuoruan/mem0-api-server

# 4. Start the dashboard
docker run -d --name mem0-dashboard \
  --network mem0-net \
  -e NEXT_PUBLIC_API_URL=http://localhost:8000 \
  -e API_INTERNAL_URL=http://mem0-api:8000 \
  -p 3000:3000 \
  ghcr.io/kuoruan/mem0-dashboard
```

> In `.env`, set `POSTGRES_HOST` to the Postgres container name or IP
> (e.g. `mem0-postgres`), not `postgres` (the Compose service name).

#### Building from source

```bash
cd server

# Build the API image (needs the repo root as build context for the mem0 SDK)
docker build -t mem0-api-server \
  --build-context root=.. \
  -f Dockerfile .

# Run it
docker run -p 8000:8000 --env-file .env mem0-api-server
```

### JSON Config Override (MEM0_CONFIG_PATH)

For complex LLM/embedder setups (custom base URLs, Ollama, etc.), point
`MEM0_CONFIG_PATH` to a JSON file. Values are **deep-merged** over the defaults
built from env vars. `$VAR` / `${VAR}` environment-variable expansion is
supported in string values.

#### OpenAI example (default provider)

```json
{
  "llm": {
    "provider": "openai",
    "config": {
      "model": "gpt-4.1-mini",
      "temperature": 0.2
    }
  },
  "embedder": {
    "provider": "openai",
    "config": {
      "model": "text-embedding-3-small"
    }
  }
}
```

#### Ollama example

```json
{
  "llm": {
    "provider": "ollama",
    "config": {
      "model": "qwen3:32b",
      "ollama_base_url": "http://192.168.1.2:11434"
    }
  },
  "embedder": {
    "provider": "ollama",
    "config": {
      "model": "qwen3-embedding:0.6b",
      "ollama_base_url": "http://192.168.1.2:11434"
    }
  }
}
```

> The `ollama_base_url` parameter is the correct field name for the Ollama
> provider in mem0's LLM/embedder config.

### Auth Config (AUTH_CONFIG_PATH)

Point `AUTH_CONFIG_PATH` to a JSON file to consolidate all auth settings,
including OIDC providers. JSON values take precedence over env vars.

Sensitive fields (`client_secret`, `jwt_secret`, `admin_api_key`) are **not**
env-expanded — `$` characters are preserved as-is.

#### Minimal example (JWT + admin API key)

```json
{
  "jwt_secret": "your-jwt-secret-from-openssl-rand-base64-48",
  "admin_api_key": "m0-admin-key-with-sufficient-length"
}
```

#### Full example (JWT + admin key + OIDC providers)

```json
{
  "jwt_secret": "your-jwt-secret",
  "admin_api_key": "your-long-admin-api-key",
  "auth_disabled": false,
  "oidc": {
    "providers": [
      {
        "name": "google",
        "issuer_url": "https://accounts.google.com",
        "client_id": "your-client-id.apps.googleusercontent.com",
        "client_secret": "your-client-secret",
        "display_name": "Google",
        "scopes": ["openid", "email", "profile"],
        "username_claim": "name"
      },
      {
        "name": "keycloak",
        "issuer_url": "https://keycloak.example.com/realms/myrealm",
        "client_id": "mem0",
        "client_secret": "$KEYCLOAK_CLIENT_SECRET",
        "display_name": "Keycloak",
        "username_claim": ["preferred_username", "name"]
      }
    ]
  }
}
```

#### Per-provider fields

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | Unique identifier for this provider |
| `issuer_url` | Yes | OIDC issuer URL (must be `https://` unless `OIDC_ALLOW_HTTP_ISSUER=true`) |
| `client_id` | Yes | OAuth/OIDC client ID |
| `client_secret` | Yes | OAuth/OIDC client secret (not env-expanded) |
| `display_name` | No | Label shown in the dashboard (defaults to title-cased `name`) |
| `scopes` | No | OIDC scopes (defaults to `["openid", "email", "profile"]`) |
| `username_claim` | No | Claim name (string) or fallback list (e.g. `["preferred_username", "name"]`) for display name |

> ⚠️ Multi-instance note: `OIDC_STATE_STORE=memory` is per-process. For
> multi-worker or multi-replica deployments, implement a shared backend
> (Redis/DB), select it via `OIDC_STATE_STORE`, and rebuild.

## Database Migrations

On container startup, `entrypoint.sh` automatically runs:

1. `scripts/prepare_db.py` — waits for Postgres to accept connections
   (exponential backoff up to 60 s) and creates the `APP_DB_NAME` database if
   it doesn't exist.
2. `alembic upgrade head` — applies all pending migrations.

Migrations live in `server/alembic/versions/`:

| Migration | Description |
|-----------|-------------|
| `001_create_users_and_api_keys` | Users and API keys tables |
| `002_create_request_logs` | Request logs table |
| `003_create_settings` | Runtime configuration table |
| `004_unique_admin_role` | Unique admin role constraint |
| `005_refresh_token_jtis` | Refresh token JTI table |
| `006_request_logs_brin` | BRIN index on request logs |
| `007_entity_permissions` | Entity permissions table |

Manual migration (if needed):

```bash
docker compose exec mem0 alembic upgrade head
```

## Authentication & Security

### Auth Methods

Three authentication methods are supported, in order of precedence:

| Method | Header | Use case |
|--------|--------|----------|
| **JWT Bearer** | `Authorization: Bearer <token>` | Dashboard login, frontend |
| **Per-user API Key** | `X-API-Key: m0sk-...` | Programmatic API calls |
| **Admin API Key** | `Authorization: Token <admin_key>` | Global admin (from `.env` or auth config) |

- JWT access tokens expire in 30 minutes; refresh tokens last 30 days.
- API keys use the `m0sk_` prefix, bcrypt-hashed at rest.
- Login endpoints are rate-limited (5 attempts/minute) to prevent brute force.
- Auth is **enabled by default**. `AUTH_DISABLED=true` is for local dev only.

### Security Headers

The dashboard sets these headers on every response:

- `X-Frame-Options: DENY`
- `Content-Security-Policy: frame-ancestors 'none'`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`

| Method | Path | Description | Auth |
|--------|------|-------------|------|

```bash
curl -X POST http://localhost:8888/search \
```

### Compat API (v1/v2/v3)

Versioned endpoints for `MemoryClient` SDK compatibility:

| Version | Base paths | Notes |
|---------|-----------|-------|
| v1 | `/v1/memories`, `/v1/memories/search` | Original format |
| v2 | `/v2/memories`, `/v2/memories/search` | Enhanced format |

| `search_memories` | Semantic search | Read |
| `get_memories` | Paginated browse | Read |
| `get_memory` | Fetch by ID | Read |
| `update_memory` | Update text/metadata | Write |

| `delete_all_memories` | Bulk delete by scope | Destructive |

| `list_events` | List operation events | Read |
| `get_event_status` | Check event status by ID | Read |

## Operations

### Reset Admin Password

```bash
cd server
make reset-admin-password EMAIL=admin@example.com PASSWORD='new-password'
```

Requires shell access to the host; does not affect existing data.

### Prune Request Logs

The `request_logs` table is append-only. Prune periodically:

```bash
# Default: keep 30 days
make prune-logs

# Custom retention
make prune-logs REQUEST_LOG_RETENTION_DAYS=7
```

Wire into cron or systemd timer for production. The `created_at` column has a
BRIN index, so range deletes stay cheap on large tables.

Background auto-pruning is enabled by default
(`REQUEST_LOG_PRUNE_ENABLED=true`), running every 24 hours.

### Logs & Monitoring

- **Log level:** set via `LOG_LEVEL` env var
- **Request tracing:** every request gets a unique `X-Request-ID`
- **Health check:** `GET /api/health` returns server, DB, and vector store status

```bash
make health     # quick health check
make logs       # tail container logs
```

### Telemetry

Anonymous telemetry is on by default (max two events per install:
`admin_registered`, `onboarding_completed`). Sends install UUID, email domain,
and server version. No PII.

Opt out: `MEM0_TELEMETRY=false`

## Migrating from ankane/pgvector

This repo replaced the archived `ankane/pgvector:v0.5.1` (PostgreSQL 15,
pgvector 0.5.1) with the official `pgvector/pgvector:pg17` (PostgreSQL 17,
pgvector 0.8.0).

**Fresh installs** — no migration needed.

**Existing installs** — PostgreSQL 17 cannot read PG 15 data files directly.
Export first, then import:

```bash
# 1. Dump all data from the old container (while it's still running)
cd server
docker compose exec -T postgres pg_dumpall -U postgres > mem0_backup.sql

# Verify the dump
ls -lh mem0_backup.sql

# 2. Stop the old stack and remove the volume
docker compose down -v

# 3. Ensure POSTGRES_PASSWORD is set in .env

# 4. Start only Postgres
docker compose up -d postgres

# Wait until Postgres is fully ready (loop, not a one-shot check)
until docker compose exec -T postgres pg_isready -q; do sleep 1; done

# 5. Restore BEFORE starting the API (otherwise Alembic creates empty tables)
docker compose exec -T postgres psql -U postgres < mem0_backup.sql

# 6. Start the API — Alembic detects existing tables, applies only new migrations
docker compose up -d mem0

# 7. Verify
make health
curl -s http://localhost:8888/memories?user_id=<your-user-id> -H "X-API-Key: ..."
```

> ⚠️ You must restore data **before** starting the API container. The API runs
> `alembic upgrade head` on startup, which creates empty tables — restoring
> after that fails with duplicate-key errors.

## FAQ

**Compose refuses to start with a POSTGRES_PASSWORD error**

docker-compose requires `${POSTGRES_PASSWORD:?...}`. Set a non-empty value in `.env`.

**API returns 401 everywhere**

Auth is on by default. Fix it by either:
1. Setting `ADMIN_API_KEY` in `.env` (fastest)
2. Registering an admin at `http://localhost:3000/setup`
3. Setting `AUTH_DISABLED=true` (local dev only)

**`JWT_SECRET is required` at startup**

Generate one: `openssl rand -base64 48`, then set `JWT_SECRET=` in `.env`.

**Using Ollama as LLM/embedder**

Set `MEM0_CONFIG_PATH` to a JSON file with the Ollama config (see
[JSON Config Override](#json-config-override-mem0_config_path)). Use
`ollama_base_url` as the config key for the Ollama server URL.

**Dashboard can't connect to the API**

Check that `DASHBOARD_URL` in `.env` matches the actual URL you use to access
the dashboard. This variable also controls the CORS allowlist.

**Port conflicts**

Defaults: 3000 (dashboard), 8888 (API), 8432 (Postgres). Adjust port mappings
in `docker-compose.yaml` if needed.
